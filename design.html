Goals

What success looks like

Our primary goal is an autonomous mobile manipulation system that can identify, retrieve and deliver objects with minimal human intervention, even when the robot and object start in different positions.

Realistic goal

Reliably retrieve one object type

Detect, navigate to, pick up and deliver a single lightweight, visually distinctive object from varied starting positions.

Reach goals

Search and generalize

Search the room autonomously when the object isn't in view, and retrieve several kinds of everyday objects.

Requirements

Requirements & constraints

Functional

  • Detect the target object in the onboard camera feed.
  • Estimate its position on the floor in the map frame.
  • Plan and drive a collision-free path to a pose where the object is within arm reach.
  • Grasp, lift and hold the object while driving.
  • Drive to the delivery location and place the object down.
  • Recover from failures (lost detection, missed grasp) without a restart.

Constraints

  • Lab time is scarce: software must be hardware-agnostic enough to develop and test away from the lab.
  • Payload and stability: the arm adds mass far from the wheelbase (see tip-over).
  • Sensor clearance: the arm and mount must not block the LiDAR or the camera.
  • Power: the arm may need its own supply while the TurtleBot drives.
  • Removable mount: the TurtleBot is a lab robot and has to go back to stock.
  • Add constraints we discover
Architecture

System architecture

Proposed ROS 2 node graph. Sensors are cyan, our nodes are lime, hardware is grey. Update node and topic names to match the final code

Perception

Runs the detector on each frame, back-projects the detection to the floor, and publishes a PoseStamped in the map frame.

Mission state machine

The only node that knows the task. It calls Nav2 and MoveIt through actions, so every step can be cancelled, timed out and retried.

Hardware-agnostic

Every node talks through standard ROS 2 interfaces, so we can swap the real robot for a Gazebo simulation or bag playback when we're away from the lab.

Average several floor-position estimates to reduce noise, then transform into the map frame.

success
Stable estimate (spread < threshold) → NAVIGATE
failure
Estimate jumps around → back to SEARCH

Navigate

Compute a grasp pose at standoff distance d from the object, facing it, and send it to Nav2.

success
Nav2 reports goal reached → ALIGN
failure
Planner fails / timeout → Nav2 recovery behaviors, then re-detect
uses
NavigateToPose action

Align (final approach)

Nav2's goal tolerance is looser than the arm's reach band, so we re-detect the object up close and creep forward or rotate until it's in the sweet spot.

success
Object inside the reach band → GRASP
failure
Object lost → DETECT
uses
/cmd_vel, /target_pose

Grasp

Pre-grasp above the object → descend → close gripper → lift. MoveIt plans each segment.

success
Trajectory finished → VERIFY
failure
IK has no solution → back up and ALIGN again
uses
MoveGroup action, gripper controller

Verify

Check the object is actually held: gripper joint position (didn't fully close) and/or the object is gone from the floor in the camera.

success
Object held → DELIVER
failure
Empty gripper → retry GRASP (max 2), then DETECT
uses
/joint_states, /detections

Deliver

Stow the arm close to the body (keeps the center of mass inside the support polygon) and navigate to the delivery pose.

success
At delivery pose → RELEASE
failure
Object dropped (VERIFY check while driving) → DETECT
uses
NavigateToPose

Release

Lower the object, open the gripper, retract, and report success.

success
Done → idle
failure

Decisions

Design choices & trade-offs

Challenges

Why this is hard

The arm can tip the robot

A TurtleBot3 Burger rests on two wheels and one rear caster. Hang an arm off the front and the center of mass can slide past the wheel axle.

Reaching the floor

The SO-101 was designed for tabletops. From a low mount, its reachable floor area is a thin ring only a few centimeters wide.

The arm blocks the sensors

Any pose the arm holds while driving can show up in the LiDAR scan as an "obstacle" or cover the camera.

Errors stack up

Camera calibration, TF, localization and Nav2 tolerance errors all add up before the gripper closes. The grasp has to tolerate a few centimeters of slop.

Try it: will it tip over?

Interactive · top-down + side view

The robot stays upright while the combined center of mass $\bar{\mathbf{p}} = \frac{\sum_i m_i \mathbf{p}_i}{\sum_i m_i}$ lies inside the support polygon of its contact points. The side view follows the plumb line from the center of mass down to the floor: once it falls outside the support span, the robot pivots on its front contact. The chart sweeps the arm's whole reach for the current pan and payload. Braking at deceleration $a$ shifts the effective center forward by $h\,a/g$, so the margin $m$ allows $a_{\max} = g\,m/h$.
